# Vela specification onboarding

Use the [visual lesson authoring guide](../engineering/visual-lesson-authoring.md) when writing or revising a lesson. It defines how to choose a representation, register a model or figure, and verify the reader experience.

Runtime tools follow the separate [module-support guide](module-support-spec.md) and `.vela/module-capabilities.json`. Mathematics is the first development area, not a universal UI requirement. Conceptual pedagogy/ethics support includes opt-in Socratic debate; universal tiered hints and its boundaries are defined in [tutor scaffolding](tutor-scaffolding-spec.md). Keep future subject extensions modular.

The four Universal Core files apply to every module; extensions only add requirements. manifest.json explicitly maps institution/moduleCode pairs to domains. MAT1512 selects mathematics and education-pck; MAT1503 selects mathematics and education-pck; COS1511 selects programming; BPT1501 selects education-pck; CHE1501 selects chemistry; CHE1502 adds organic chemistry. PHY1505 and PHY1506 select physics; PHY1501 retains its legacy profile. CHE1503 and PHY1503 add the [laboratory practical extension](laboratory-practical-spec.md). TPS2601 uses the [teaching-practice extension](teaching-practice-spec.md), and each Group B option uses the [communicative-language extension](communicative-language-spec.md). See the [90104–PSM module index](../modules/UNISA/90104-PSM.md). The chemistry/physics profile is defined in [science content spec](science-content-spec.md). No prefix inference is used. Unknown profiles fail closed. A deliberately domain-neutral profile can use an empty domains list while retaining the Universal Core.

To add a module, register its exact institution and code with domain names. To add a domain, add a policy Markdown file and a domains entry with file, optional minSessions, sessionSections and unitPatterns. Interactive component implementations and their safety checks remain separate from policy files. Never expose the trusted filesystem root override to client requests.

Increment the manifest version when policy changes. Effective SHA-256 hashes include the exact selected policy bytes, profile and structural requirements, so edits change the hash even if a version bump is missed. Store version and hash with published revisions. Standards references are authoritative starting points, not proof of compliance; record specific source/version and reviewer evidence per module.

The quality gate checks structure, KaTeX syntax, registered visuals, likely private identifiers and eight-word source-prose overlaps. It does not certify semantic correctness, originality or legal compliance. Offline audit warns when the source corpus is absent; source-backed publication must requireSourceAudit:true and supply it. Independent calculation and editorial review supplement these checks.

Preflight all units before writing, then publish atomically. Keep OCR/source evidence separate from original lessons, and preserve stable learner and unit identities and milestone positions.

Source-audit corpora must contain at least one eight-word prose window after excluding math and fenced code; empty, whitespace-only, formula-only and uniformly short inputs are reported as unavailable. For publication with visual hooks, callers must pass their actual supported-component registry through allowedVisuals. Omitting that option does not validate hooks or report a completed registered-visuals check.

Version 1.1 requires Learning goal, Prerequisites and Why this works / conditions as substantive visible teaching. All worked examples, assessment questions and prediction answers use the shared question-first exercise protocol; answer reveal does not establish mastery. The runtime tutor validates the active persisted authored session against its unit and uses that authored teaching alongside source RAG. Navigation preserves qualification/module/unit/session hierarchy. The structural audit cannot certify those runtime behaviors; integration tests must verify them.
